## Authority and boundary

The design authority is `docs/specs/2026-08-27-febio-llm-cae-harness-design-v2.md`, with the P1 planning authority in `docs/plans/2026-08-27-febio-cae-harness-greenfield-plan.md`. This slice follows the explicit typed-intent and canonical-boundary rules in design sections 5.1--5.3 and the CT-01 CaseSpec composition gate in the plan.

`CaseSpec` composes eleven existing typed owners: geometry, one of the two public concrete material types, supports, rigid tool, motion, contact, mesh policy, solver policy, output policy, quality policy, and budget. It consumes each child owner's public canonical bytes and does not duplicate private selection or semantic-set serialization. Its local checks use only explicitly supplied identities and frames:

- part selections must match the declared geometry digest/body/frame;
- support selections, contact part surface, local refinements, output requests, and output evaluations must resolve to the declared part or rigid tool identity as allowed by the contract and use the common placement frame;
- rigid-tool body and part body IDs must be distinct, while rigid-tool placement, contact pair frame, and motion direction frame must match the geometry placement frame;
- contact tool surface must be canonically equal to the rigid-tool contact surface, including unordered child-set semantics;
- every quality criterion evaluation ID must resolve to an output evaluation ID; and
- every saved output time must lie within the inclusive motion sample time interval after SI conversion.

The implementation deliberately does not infer physical meaning, read files, resolve selections, calculate tool digests from recipes, add supports, determine numerical profile compatibility, or perform readiness, registration, evidence freshness, display-frame, geometric-coverage, compiler, solver, or result-receipt checks. The existing pure kinematic compatibility function remains separate; unsupported execution-profile DOFs are not rejected by this structural composition boundary.

## Implemented contract

`CaseSpec` is a frozen, slotted dataclass with all eleven fields mandatory. Omitting a mandatory Python call argument raises the generated initializer's standard `TypeError` before `__post_init__`, with the missing field named. Supplying `None`, a mapping, string, boolean, or other wrong-typed child raises `CaseSpecValidationError` with the offending field in context. Only `IsotropicLinearElastic` and `CompressibleNeoHookean` are accepted for `material`.

The constructor forces every child through its public `to_bytes()` projection before performing cross-object checks and then forces the complete parent canonical projection. `to_dict()` returns a detached normalized projection and `to_bytes()` returns deterministic shared-schema-1 canonical bytes. Caller mutations and mutations of returned nested projections do not alter the retained typed intent. Existing child owners remain responsible for SI normalization and ordered versus unordered semantics.

The original focused scope covered 32 cases: every wrong child independently, both material types, part/support/contact/tool identity and frame relations, non-first collection entries, a valid explicit support transform, tool-surface canonical equivalence and mismatch, local refinement/output/evaluation selection identities, quality evaluation resolution, SI-equivalent saved and motion times, out-of-interval saved times, unresolved selections, canonical permutations, changed identity bytes, detached projections, and unsupported kinematic intent. R1 adds 17 cases: eleven standard-TypeError omission cases, four parent-boundary surrogate-evidence cases, one explicit ordinary-Unicode positive, and one post-composition caller-owned-collection mutation case. The R1 focused run therefore collected 49 cases; no new behavioral RED was manufactured for unchanged production.
