文書版：0.4／作成日：2026-09-07／改訂日：2026-09-15／状態：製品契約。実機適合性の認定状況は[実装計画書](../plans/2026-09-14-febio-cae-harness-greenfield-plan.md)の現在地表を参照する。

## 1. 目的と対応範囲

STEP部品に対し、寸法・配置を指定して生成した剛体治具を押し込み、FEBioで変形を解析する。条件入力・部分変更、実行、XPLT表示、変更前後の比較を単一のケース内で追跡し、設定根拠・解析モデル・実行・結果を再現可能にする。

### MVP（最初のゴール）

MVPの目標は、新規環境へ通常インストールしたwheelのCLIから、次の1経路が最初から最後まで一貫して通ることである。

| 項目 | MVPの範囲 |
|---|---|
| 入力 | 合成STEP 1個、閉じたソリッド1つ。単位および対象ボディは明示 |
| 治具 | 直方体1つ、`AsPlaced`（指定位置のまま）配置 |
| 材料 | 等方線形弾性（ヤング率・ポアソン比・適用根拠を明示） |
| 支持・接触 | XYZ完全固定支持、部品と治具の1組、摩擦なし |
| 運動 | World座標の−Z方向への単調な変位制御、準静的 |
| 操作 | `create → inspect --native → provision-planar-profiles → spec → prepare-planar → validate → freeze → run → status` |
| 品質 | 必須項目のうち「実行・結果の完全性」「接触品質」「忠実性」「釣り合い」「ソルバー残差」の5項目を判定。「メッシュ依存性」は `UNVERIFIED` の状態にとどめ、`COMPLETE` を許容 |
| 表示 | CLIがFEBio Studioを起動して対象XPLTを開き、`LAUNCHED` を記録 |
| 変更・比較 | ヤング率のみを変更した子版を既存メッシュで再解析し、反力―移動量曲線と部品変位を比較 |

条件入力は型付きJSON（`case spec`）で行う。日本語文やLLMによる入力（`case intent / answer / edit`）はMVPに含めず、実装済みの範囲を維持したまま後続工程で扱う。

初回の `prepare-planar` は観測した形状・選択集合・生成メッシュを仕様へ結び付け、検証と不変版の確定も行う。準備前にメッシュ未登録の版を凍結したことにしてはならない。準備後の公開 `validate` と `freeze` で `READY` および同じ準備済み不変版を確認する。

### 目標範囲（MVP後）

| 項目 | 目標範囲 |
|---|---|
| 環境 | Windows、Python 3.12、GUIなしのCLI。FEBioおよびFEBio Studioは外部導入 |
| 治具 | 球・円柱・直方体の剛体1つ。初期接触配置の自動計算 |
| 材料 | 等方線形弾性、圧縮性Neo-Hookean |
| 接触 | 摩擦なし、または明示された一定Coulomb摩擦 |
| 出力 | 部品変位、応力・ひずみ、治具移動・反力、接触診断、XPLT |
| 編集 | 材料、支持・接触領域、摩擦、治具、運動、メッシュ、評価条件の変更 |
| 入力 | 日本語による条件入力・質問・回答（型付き提案） |
| 品質 | メッシュ依存性を含む6項目の判定 |
| 表示 | Studioでの表示内容を独立して確認した `CONFIRMED` |

公開対象とする組み合わせは、実測に基づくバージョン・機能・数値設定と証拠を紐付ける対応表（プロファイル）によって限定する。対応表にない現象は未対応として返す。

塑性・損傷・粘弾性、動解析、除荷・繰り返し負荷、多数部品間の接触、シェル要素化、解析途中の再メッシュ、自由形状最適化は対象外とする。元STEPモデルの自動編集は拡張工程で扱う。

### 完了の定義

解析タスクは、要求された終端への到達、結果の完全性、必須数値品質、および指定された表示確認がすべて揃った時点で `COMPLETE` となる。物理的な実物照合の状態は個別に表示する。未完了の場合は到達点・理由・次に取るべき操作を返す。製品全体の完成条件は計画書の定めに従う。
MVPの製品完了判定では、自動E2Eのログ・receiptを手動8手順の代用にしない。操作者が公開CLIの各コマンド、終了コード、ID、FEBioログ、Studio画面とGit外PNGを記録し、欠測を`UNVERIFIED`として理由付きで保持する。

## 3. 構成と共通契約

単一のPythonパッケージの中核に共通型を配置し、外部ツールはアダプターによって分離する。

| 所有モジュール | 責務 |
|---|---|
| `domain` | 型、ID、単位、状態、不変条件、正規化の定義（外部ツールは呼び出さない） |
| `application` | 登録、検証、状態遷移、実行権限、依存関係の順序制御 |
| `adapters.geometry`／`meshing` | STEP調査、領域定義、剛体生成、メッシュ分割、品質検証、節点順序の変換 |
| `adapters.febio`／`viewer` | FEBioの入力生成・実行・結果読込／外部Studioとの表示連携 |
| `adapters.llm` | 構造化提案、質問の生成、診断および結果の説明 |
| `storage`／`cli` | SQLiteおよび不変ファイルによる永続化／共通サービスを用いた日本語表示およびJSON出力 |

採用技術はGmshのPython API、OpenCASCADE、Pydantic、標準SQLiteとする。外部処理は所有する子プロセス内に隔離して実行する。

Gmshの実行時依存検証は、検証済みソースが持つ任意importとフォールバックの意味を保持する。新規の `native` 環境で、NumPyが未導入でも公式Gmshソースが非NumPy経路を選択できる場合、未導入だけを理由に必須依存不足と判定しない。選択されたimport・定義元・別名の同一性、未導入の事実、および選択を制御する初期フラグと未束縛名を照合する。必須importの欠落、認証失敗、差し替えを任意依存の欠落として扱わない。静的に裏付けられない分岐は実行せず、未対応として拒否する。

### 永続データ

| 型 | 保持する情報・不変条件 |
|---|---|
| `EvidenceRef` | 出典、対象フィールド、元情報のハッシュ。ユーザー指示または登録資料へと解決可能 |
| `CaseDraft` | 草案ID、世代、確定値、未解決項目。世代一致に基づく比較交換（CAS）によって更新 |
| `IssuedQuestion` | 質問ID、草案・世代、対象、根拠集合。該当する世代において一度だけ適用 |
| `CaseRevision` | ケース・親版、仕様、根拠、仕様ハッシュ。凍結後は不変 |
| `SelectionRef` | 名前、役割の根拠、形状版、座標、選択規則、解決結果 |
| `MeshArtifact` | 形状・生成条件・ツール、要素・集合・品質および内容ハッシュ |
| `ExecutionBundle` | ケース版、すべての実行入力、設定、対応ツールおよび内容ハッシュ |
| `AttemptRecord` | 試行・実行・入力、所有世代、プロセス、数値設定、状態および履歴 |
| `ResultManifest` | 試行・入力、固定済み出力のパス・サイズ・ハッシュ、読込結果 |
| `QualityAssessment` | 結果、評価方針版、値・判定・未検証理由。再評価時は新規に記録 |
| `ComparisonSpec` | 比較対象の実行、意図した変更、固定条件、軸・領域・単位・集計方法 |
| `PreviewReceipt` | 結果・XPLT、Studio版、観測要求・状態・読込根拠 |

すべての永続契約に `schema_version` を付与し、共通の正規化実装によってハッシュを計算する（実装ノート §10）。共通型および状態の所有者は単一とし、アダプターの成功フラグよりも共通状態を正とする。

### ケース仕様・根拠・単位

`CaseRevision.spec` の必須構成は以下のとおりである。

| フィールド | 内容 |
|---|---|
| `geometry` | STEPハッシュ、対象ボディ、単位、座標変換、調査結果 |
| `material` | モデル、単位付き係数、出典、ひずみ・変形速度の適用根拠 |
| `support` | 領域および拘束自由度 |
| `rigid_tool` | 形状、正の寸法、位置・姿勢、接触面、6自由度 |
| `motion` | 単位方向ベクトル、単調移動履歴、基準位置、準静的適用の根拠 |
| `contact` | 接触両面、摩擦モデル・係数、初期配置の意図 |
| `mesh_policy`／`solver_policy` | 要素種別、全体・局所サイズ、品質・細分化上限／対応設定、許容差、増分、再試行条件 |
| `outputs`／`quality_policy` | 対象場・履歴・状態・評価要求／終端、接触、釣り合い、メッシュ依存性の判定基準と根拠 |
| `budget` | 経過時間、試行回数、CPU使用量、LLM呼出し回数・トークン数の上限 |

必須となる物理条件は、すべて明示的な値と根拠を保持する。摩擦なし、回転固定、全体評価、隙間ゼロといった条件も、明示値として登録する。不明な必須物理条件がある場合は、質問を通じて解消する（`ASK_AND_BLOCK`）。検証済み範囲内の数値設定はサービス側で選択可能であるが、物理条件や負荷履歴は利用者の明示値のみに基づいて決定される。

物理量は値と単位をペアで保存する。STEPファイルの単位と明示指示との競合を解消し、CADからFEBioへの変換内容を記録したうえで、SI整合単位系で出力する。表示単位は保存記録から変換する。配置・運動・力・評価に用いる各座標系はIDによって指定し、方向ベクトルを正規化する。

## 4. 形状・準備・メッシュ

### STEP調査

`case --state-dir STATE inspect CASE_ID --native [--wall-seconds SECONDS] [--cpu-workers N] --json` はケース作成直後から利用可能であり、物理条件、選択済みボディ、対応表の指定を要求しない。ボディ、閉じたソリッド、単位、座標、体積、面、欠陥の有無を観測して返す。結果は `INSPECTED`、`native_qualification` は `UNVERIFIED` とする。ツールバージョンやAP214の照合、リソース上限、応答検証については、実装ノート §1–2 に従う。

### 領域・治具・接触

領域はCAD属性、明示的なボディと座標条件、またはユーザー選択面によって指定する。元形状のハッシュ、解決面、面積・重心などを保存し、再メッシュ後も非空性・対象・被覆性を検証する。形状変更後に一意な再対応付けが不可能な場合は、未解決状態へと戻す。

治具形状として、球は半径、円柱は半径と高さ、直方体は3寸法を指定する。位置・姿勢と運動方向を分離して扱い、初期接触配置は指定された領域・方向・隙間から一意に定まる場合にのみ計算して記録する。治具の並進3自由度および回転3自由度は、固定・指定運動・明示的な自由のいずれかへと解決する。

部品と治具は個別にメッシュ化し、接触節点を共有させない。治具はFEBioにおける剛体として扱う。接触方式、主面・従面（`primary/secondary`）、法線方向、摩擦、ペナルティ係数、探索設定は、対応表に準拠して保存する。

### 平面準備

`case --state-dir STATE prepare-planar CASE_ID --file REQUEST --expected-generation N [--parent-revision-id ID] --json` は、`SpecUpdateRequest` の型付き部分仕様・根拠・出典宣言を受け取り、部品のTet10メッシュおよび治具の剛体メッシュを生成して `PREPARED` 記録を公開する。呼出元からのメッシュデータや生成証明の直接受け入れは行わない。計算資源の上限および予約処理は実装ノート §3 に従う。

| 派生操作 | 契約 |
|---|---|
| ヤング率だけの変更 | 同一ケース内の登録済み親、親仕様ハッシュ、祖先関係を検証し、等方線形弾性のヤング率および必要な根拠以外は不変とする。元の準備済みルートに紐付け、メッシュを再利用する |
| メッシュ細分化 | `--parent-revision-id` により登録済みの準備完了親を指定する。あらかじめ宣言された「粗→中→細」の順序に従い、次の `global_size` のみを変更して、固有の子版および生成記録を作成する |

親版、過去のメッシュ、過去の結果、過去の生成記録はすべて不変である。

### 対応表の登録

`case --state-dir STATE provision-planar-profiles CASE_ID [--bundle-path BUNDLE] --json` は新規登録ケースへ対応表を登録する。`--bundle-path` を省略すると製品組み込みの既定対応表（ソルバー・出力・品質のプロファイルとメッシュ品質基準）を登録し、指定すると外部バンドルの内容を検証してから登録する。ソルバー・出力・品質・メッシュ品質の `NumericalProfileRef` を返し、`PROVISIONED` は登録完了を示す。同じID・同じ内容の再登録は成功し、異なる内容は競合として拒否する。限定範囲の内容は実装ノート §3。

## 5. 入力生成・実行・出力固定

コンパイラは、登録済みの不変版、検証済みメッシュ、および対応表から `.feb` と出力要求を生成し、面、材料、領域、剛体、負荷制御、出力変数を照合する。実行直前にサービス側で草案世代、版、根拠、入力データ、予算を再検証したうえで実行権限を発行する。すでに明示されている条件や許可事項について、再度の確認は求めない。

草案状態は `DRAFT / NEEDS_INPUT / READY` とする。実行は `CREATED → PREPARING → RUNNING → DRAINING → VALIDATING → SUCCEEDED` を基本状態とし、失敗・取消し・中断は `FAILED / CANCELLED / INTERRUPTED` として区別する。`SUCCEEDED` は終端への到達と出力の完全性を示し、数値品質および表示確認の判定とは独立して保持する。

所有プロセス群を識別して一元管理し、正常終了・取消し・タイムアウトのいずれにおいても、子孫プロセスおよび書込処理が完全に終了した後に結果を検証する。クラッシュ発生時は永続状態と所有権を照合し、確認が取れない場合は中断状態のまま復帰させる。再試行にあたっては、新規の試行および空の新規出力領域を用い、履歴と残存予算を継承する。その際、変更が許可された増分・反復・接触に関する数値設定のみを調整し、物理条件と負荷履歴は維持する。再解析は必ず初期状態から実行する。

終了コード、ログ、解析終端、要求された出力を総合して判定する。書込処理の終了後に出力を固定し、改変・切詰め・差替えを検知したうえで、結果一覧を一度だけ不可分（アトミック）に公開する。ファイル上限については実装ノート §4 に従う。

## 6. 結果と数値品質

### 指標

| 指標 | 定義 |
|---|---|
| 治具移動量 `q` | 初期位置からの並進変位を指定押し込み軸へ射影した値 |
| 抵抗力 `F` | 同一軸へ反力を射影し、抵抗方向を正とする検証済み符号へ変換した値 |
| 部品変形 | 指定領域・状態における変位ベクトル、成分またはノルム、および明示的な集計値 |
| 食い込み | 離間を正とするgapへ正規化した `max(0, −gap)` |
| 応力・ひずみ | 測度、成分、座標系、格納位置を固定して定義 |
| 接触開始 | 明示された閾値および判定法によって定義される最初の接触状態 |

総移動量と、初期隙間を除いた実質的な押し込み深さは、別個の評価軸として扱う。

### 必須項目と判定

数値判定結果は `PASS / FAIL / UNVERIFIED / NOT_APPLICABLE` とする。未検証の理由および不適用の根拠は必ず記録する。公開される解析結果においては、以下の6項目を必ず評価する。

| 必須項目 | 合格に必要な根拠 | MVPでの扱い |
|---|---|---|
| 実行・結果の完全性 | 成功した試行と版、入力、メッシュ、対応表、読込器、結果がすべて一致し、要求されたすべての実体、成分、配置、座標系、単位、状態が解析終端まで有限値として揃っていること | 必須 |
| 接触品質 | 要求された区間での接触状態、初期干渉、隙間および食い込み量が明示された許容限界内にあること | 必須 |
| 運動・支持・接触集合の忠実性 | 治具の軌跡、剛体の位置、支持自由度、選択集合が指定内容と一致していること | 必須 |
| 準静的釣り合い | 対象とする力系、作用側、符号が検証された反力と外力が、各状態において釣り合っていること | 必須 |
| ソルバー残差 | 当該バージョンに適合する読み込みが行われ、採用されたすべての増分、ならびに非線形・拡張ラグランジュ反復の残差が、規定の数値方針と整合していること | 必須 |
| メッシュ依存性 | 指定された評価量に対するメッシュ細分化および比較検証が、事前の判定基準を満たしていること | `UNVERIFIED` を許容 |

各項目には、適用範囲が検証された判定処理と、該当する実行に紐付く証拠が必要となる。証拠不足または適用範囲外の場合は `UNVERIFIED` とする。材料・負荷・支持の適用根拠および実物照合の結果は別行に記載する。各判定処理の具体的な内容は実装ノート §5 に従う。

`quality_registration_status` は評価登録の利用可否を示し、`quality_status` は必須項目を含めた数値判定を示す。既知の `FAIL` は他項目の `UNVERIFIED` よりも優先して扱われる。実行自体が成功していても必須品質が不足している場合は `NEEDS_QUALITY`、不合格の場合は `FAILED`、品質基準を満たしつつ必要な表示確認のみが不足している場合は `NEEDS_PREVIEW` とする。なおMVPにおいては、source-local metricが存在しないcanonical global mesh producerの`mesh_dependence`だけは`UNVERIFIED`を許容し、他の5項目が`PASS`であれば品質合格と判定する。明示的に宣言されたsource-local rowはcriterion IDが`mesh_dependence`でもstrictに扱い、ID衝突でoptional扱いへ変換しない。

## 7. 表示・編集・比較

### Studio表示

`case preview` は、対象となる解析結果のXPLTファイルを外部のFEBio Studioで開く。状態は `REQUESTED / LAUNCHED / CONFIRMED / FAILED` とする。

| 状態 | 意味 |
|---|---|
| `LAUNCHED` | CLIが登録済みのStudio実行ファイルを起動し、現在のXPLTハッシュに一致するファイルを引数として渡した状態。MVPにおける表示確認は、この段階で完了とする |
| `CONFIRMED` | 表示された変数、成分、座標系、単位、最終状態が独立した観測によって確認された状態。目標範囲における要件であり、観測プロトコルは実装ノート §7 に従う |

`LAUNCHED` の起動記録には実行ファイルの絶対パス・SHA-256、PID、起動時刻、および取得できた版を保存する。実行ファイルに版情報がない場合は版を `UNVERIFIED` として理由を明記し、版番号を推測しない。この記録はプロセス起動と対象ファイルの引き渡しだけを証明し、Studioの版認定や表示内容の `CONFIRMED` を意味しない。

`preview-status` は、保存済みの記録を再検証する。

### 部分変更

`CasePatch` は親仕様ハッシュ、許可された変更パス、型、および根拠を保持する。元の版、入力、結果はそのまま保存され、過去の親版に対する差分適用は拒否される。Studioなどで直接編集された `.feb` は、管理対象の仕様には取り込まない。

| 変更 | 必要な処理 |
|---|---|
| 材料・摩擦・支持・運動 | 物理条件および領域の再検証、入力生成、解析実行、結果評価 |
| 治具形状・配置・メッシュ | 影響を受ける形状・領域・メッシュ以降の各工程を再生成 |
| 評価状態・集計・表示 | 既存の出力で充足する場合は、新たな評価のみを作成 |
| 未保存の変数・状態 | 出力要求を変更した版を作成し、初期状態から再解析 |

MVPにおいて実装済みの変更操作は、ヤング率の置換およびメッシュの再利用である。

### 比較

比較条件としては、双方の解析結果、意図した差分、固定条件、共通区間、移動量または接触後の押し込み深さ、評価領域、単位、応力・ひずみの測度、および集計方法を厳密に固定する。単調変化する履歴の共通軸に基づいて補間を行い、その補間方法を記録する。外挿は行わない。異なるメッシュ間の比較には領域集計、共通の物理位置、検証済み写像を用い、写像誤差および未被覆領域を明示する。

初期段階で必須とされる出力は、特性曲線と領域集計である。差分画像は、検証済み写像が存在する場合にのみ作成する。基準値がゼロである相対差は未定義として扱い、絶対差を表示する。意図しない条件差を含む結果や、計算途中・低品質な結果は、同等の結果として比較・順位付けを行わない。

## 8. LLM・CLI

### 提案と物理根拠（目標範囲）

LLMには、必要な形状要約、明示された条件、未解決事項、差分、集計値、および関連ログのみを渡す。CADデータ全体、認証情報、すべての会話履歴などは送信しない。また、提示資料に含まれる指示をそのまま操作権限として昇格させることはない。LLMから返される型付き提案については、サービス側で根拠、単位、参照関係、対応範囲、親版、計算予算を検証し、任意のPythonコード、シェルコマンド、XMLの実行や、外部パスへの書き込みは一切許可しない。

公開インターフェースは `case intent / answer / edit` とする。共通の必須引数はケースID、`--expected-generation`、`--operation-id`、`--llm-settings`、`--text` である。質問への回答には `--question` が、編集操作には `--base` がそれぞれ追加で必要となる。ユーザーの意図や回答のみから自動的に仕様を凍結したり、解析を自動実行したりすることはない。LLMを使用しない `case spec` においても、同一の登録・検証・凍結サービスを利用する。

確定した構成要素を草案に反映し、不足している項目は世代管理された単一の質問として集約する。すでに取得済みの事実を明示することで重複した質問を防ぎ、元の発言内容は不変の出典として保持する。回答内容は既知の事実と新たな事実の双方から再導出し、該当する質問を一度限り消費する。受理可能な文法、接続設定、利用予算については実装ノート §8 に従う。

### 操作と状態

| 操作 | 契約 |
|---|---|
| `--version`／`doctor` | バージョン情報、実行可能ファイル、対応表、システム機能状態の確認 |
| `case create --case-root PATH --cad PATH` | 許可された領域へのケースおよび入力データの登録 |
| `case inspect`／`prepare-planar`／`provision-planar-profiles` | 第4節に規定する形状観測・メッシュ生成・対応表登録の実行 |
| `case spec --file JSON --expected-generation N` | 型付き仕様および根拠の世代一致に基づく更新 |
| `case patch --file JSON --expected-generation N` | 親版に紐付く `CasePatch` の適用 |
| `case intent`／`answer`／`edit` | 上述の共通引数および根拠規則に準拠した草案の更新（目標範囲） |
| `case validate`／`freeze` | 仕様の再検証および不変版の作成 |
| `case run --revision-id ID --solver EXE [--preflight]` | 準備済み版の実行（MVPにおける `run-demo` からの昇格。実装状況は計画書を参照） |
| `status`／`cancel`／`resume` | 実行状態の参照、所有するプロセスの停止および復旧 |
| `case preview --manifest-id ID --studio EXE` | 対象XPLTをStudioで開き、`LAUNCHED` を記録 |
| `case preview-status --preview-id ID` | 登録記録、解析結果、および品質内容の再検証 |
| `compare BASE CAND --case-id ID --spec PATH` | 基準実行・候補実行および型付き比較条件に基づく、数値データ・曲線・報告書の生成 |

各操作は `--json` を保持し、結果として `schema_version, status, case_id, revision_id, run_id, diagnostics, next_actions` を返す。非該当のID項目はnullとする。また、実行応答時には `run_status, quality_status, preview_status, task_status` も併せて返却する。

| 終了コード | 意味 |
|---|---|
| 0 | 操作成功。ただし状態読取の成功は、解析完了そのものとは区別する |
| 2／3 | 入力・数値設定・比較条件の不正／必須物理条件の確定待ち |
| 4／5 | 環境不備・未対応機能／実行時エラーによる失敗 |
| 6／7／8 | 完全性・必須品質の不合格／処理の取消し・中断／競合の発生・古い世代の指定 |

`task_status` は、サービスが保持記録から導出する `READY / NEEDS_INPUT / RUNNING / NEEDS_QUALITY / NEEDS_PREVIEW / COMPLETE / FAILED / INTERRUPTED` である。必要な機能、APIキー、モデル、対応表などの欠落は環境エラー（終了コード 4）として扱い、物理条件に関する質問待ち（終了コード 3）とは明確に区別する。完了状態はすべて記録から一意に導出されるものであり、利用者が直接手動で書き換えるインターフェースは存在しない。

## 9. 保存・信頼境界・再現性

製品コードと実際の解析ケースは明確に分離し、各ケースは明示的に登録されたルートディレクトリ配下に保存する。ケース配下では、入力の出典、凍結された版、形状データ、メッシュ、実行および試行履歴、結果一覧、品質評価、比較結果、表示記録を一元管理する。SQLiteによる台帳管理と不変ファイルを組み合わせることで、「準備→固定→公開」の処理途中で予期せず停止した場合でも、安全に復旧可能な形で記録を保持する。

ファイルパスは登録されたケースを起点として解決し、書き込みや削除を行う前には、正規化されたパス、既存リンクや再解析ポイントの有無、および自身の管理範囲内であることを確認する。元のCADデータは常に不変として扱う。実際の `02_CAE` への書き込みは、最終的に許可された実モデル試験のみに限定する。開発・テスト用の形状データは `.local/synthetic` などに出力する。

初期の想定環境は単一ユーザーのPCであり、実行アカウントおよび製品コード自体は信頼できる前提とする。誤った上書き操作、既存リンクの存在、協調的な同時実行、原子的（アトミック）な保存処理、およびクラッシュからの復旧に対応する。ただし、同一アカウント上で意図的に妨害を行う悪意ある別プログラムへの対策は対象外とする。

Gitリポジトリには、実際のCAEモデル、解析結果、認証情報、デスクトップ環境の状態などを含めない。合成データを用いたテストにおいては小規模な生成コードのみを管理対象とし、自動生成されたCAD、FEBioファイル、XPLTは追跡対象から除外する。このため、除外設定（.gitignore）、境界スキャナー、コミット対象の事前確認を組み合わせて運用する。

使用したバージョン、ハッシュ値、数値設定、スレッド数、乱数シード、経過時間、ピークメモリ使用量、要素数、増分・反復・再試行の各実績、ならびにLLMの呼出し回数・トークン消費量を詳細に記録する。処理の実行中であっても、現在の状態、到達位置、残存予算を常時取得可能とする。なお、外部処理におけるビット単位での完全な再現性は前提とせず、結果の比較には事前宣言された許容差を用いる。

## 10. 拡張と未確定事項

ST-01は `DesignSpace / GeometryRecipe / ObjectiveSpec / OptimizationStudy` における拡張点と位置付ける。P7完了後、明示された寸法、領域、操作内容、上下限値、および保持条件を備えた編集レシピ、または元CADのパラメータAPIを用いて形状を更新する。候補形状の生成、CAD制約の検証、同一解析条件下での実行、品質検証、および新たな観測データの追加というサイクルを反復する。最適化フレームワークとしてはBoTorchを有力な候補とする。生成の失敗、非収束、低品質な結果は、理由を付記したうえで欠測値として処理する。最終選定された候補については、新規解析およびメッシュ細分化によって妥当性を検証する。

現時点における未確定事項としては、実機環境におけるFEBio・Studio・Gmshの対応範囲、材料特性・Tet10要素・接触条件の組み合わせの妥当性、XPLTのファイル形式・圧縮方式・配置構造・独立した符号照合手法、使用マシンの計算資源および性能、実部品における物理条件、ならびにBottomFrameの正式入力・許可領域・評価条件が挙げられる。各工程の進捗および現在のステータスは、計画書において一元管理する。
